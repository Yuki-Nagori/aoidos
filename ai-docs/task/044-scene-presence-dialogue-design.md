# 044 — 场景角色在场与定向交互设计

## 目标与背景

030 的 Rust / Tauri / TypeScript 提交入口已允许玩家显式选择当前场景登记的固定角色，但完整目录身份不代表角色此刻在场。动态 NPC 也尚无可恢复的场景在场关系。需要先定稿可信在场状态、输入目标选择及其与 `told` 证据的边界，再由独立实现任务接入产品；不扩大 023 或已交付的 025。

## 范围与非目标

范围：设计可信场景在场集合及 revision、固定 / 动态角色进入与离开、可信观察 / 传闻事件来源、当前输入目标选择和过期选择拒绝、目标如何沿恢复链保持，以及这些事实何时足以形成获知证据。

非目标：不实现运行时代码、动态 NPC 生成规则、记忆候选 / 别名处理或记忆专属 IPC；不将实体已登记、同场景或玩家自由文本自动视为角色观察 / 获知证据；不修改 023、025 的既有交付范围。

## 前置条件与待决策

008、012、023、043 已定稿 / 实现；030 已有 `told` 消费与候选校验，但观察 / 传闻必须先有可信事件源。设计需检查 SceneCatalog / WorldMutation / 有效因果路径的现有能力，缺少可信状态载体时先定其单向扩展点，禁止 UI 或记忆模块成为在场状态来源。依赖图固定为 043 身份 → 045 场景状态 / 获知事件 → 030 证据校验与门控；046 仅把 030 的现有定向入口接到 UI，不反向成为证据来源。记忆专属命令与查询由 031 接入。

## 设计产出

1. 冻结场景在场身份的权威来源、固定 / 动态角色成员关系、进入 / 离开规则、快照 revision、事务回执和分支回退 / 恢复行为；剧本 `actor_ids` 只表示可用身份，不默认表示正在场。
2. 定义受限的角色可选项快照及 stale / absent / unknown 选择处理，保证拒绝发生在玩家输入追加前；只要完整目标已写入 `RoundAccepted`，恢复 / 重生成沿用原目标，不重新校验成另一个角色。
3. 冻结可信获知事件契约：观察事件须带明确主体、观察范围、场景 revision 和来源因果位置；传闻须带当前告知者、原始主张来源、逐跳交付记录、传播规则及不确定性。模型正文、同场、目录登记和自由文本不能产生这类事件。
4. 规定只有完整成功且当前有效因果路径上的已提交回合可作为新获知来源；恢复只重建已提交事件，不从 partial / failed / cancelled 响应补发事件。回退使被撤销分支上的事件失效；旧 UI 响应不能回写当前快照。
5. 更新 `turn-state-machine.md`、`record-engine.md`、`ui-shell.md`、`memory.md`、`ipc-contract.md` 与架构总览；记录依赖图，保持 043 → 045 → 030 → 046 单向，避免 023 / 025 回环。

事件身份 / 字段按以下约束定型：

| 事件                   | 必需事实                                                                                                                                                                                 | 来源与接纳条件                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scenePresenceChanged` | 稳定 `entityId`、`sceneId`、enter / leave、旧 presence revision、注册规则及版本、`mutationId`                                                                                            | 仅由已注册规则作为 `SettlementPlanned` 中的版本化 `WorldMutation` 提出；与应用状态及 applied 回执原子提交。初始成员由绑定 `scriptRevision` 的 `PresencePolicy.initial` 配置；新场景成员由该 Scene 的可信 entry rule 随 `sceneAdvanced` 意图建立。两者均不从 `Scene.actor_ids`、Markdown、`entities.json` 或 `entityCreated` 推导；动态实体必须显式进入。                                     |
| `observed`             | 引擎 `evidenceId`、知情角色 ID、来源 `SourceRef`、明确 `scopeId`、动作时 presence revision、触发规则 ID / 版本、事件 mutation ID                                                         | v1 规则将 scope 绑定到当前 scriptRevision 下的具体场景，并只允许引用该场景的已完成公开旁白；`SourceRef` 的 UTF-8 字节区间标出实际依据。角色须在来源记录发生时位于该场景，不能引用其他场景正文、玩家输入或角色私语。按 settlement mutation 顺序以动作时的临时 presence 状态判断；未知规则、错误来源类别或越界区间拒绝。事件与成功完整回合的 settlement 同一因果链且已应用后才可作为记忆证据。 |
| `rumorDelivered`       | 引擎 `evidenceId`、接收角色 ID、informant ID、当前交付 `SourceRef`、根主张 `SourceRef`、前一跳 evidence ID（根来源为直接登记输入时为空）、规则 ID / 版本、不确定性标记、事件 mutation ID | 每次交付均为单独登记的版本化 mutation；接收者须在交付规则要求的在场状态中。前一跳必须属于当前有效路径、其接收角色必须等于本跳 informant、根主张及范围必须完全一致且先于本跳；最多 8 跳，同 session 内不得成环。缺失 / 回退任一跳、跨 session、顺序错误或来源不完整时整条证明链无效。根来源只证明“某人提出该主张”，不能把主张升级为世界事实。                                                 |

三个事件均写入 023 的有序意图 / 回执协议，不作为 LLM 正文标签或 UI 写入。presence 由已 applied 且在当前有效路径的变更重建；即使该变更之后回合以 failed / cancelled 结束，也不撤销已提交世界状态。获知事件的资格更严格：只有完整成功回合、对应 mutation 已 applied、来源与事件在当前有效路径且可复核时，030 才向候选提供证据。恢复只补做已持久 intent，不因恢复动作本身生成新事件；恢复 / 重生成产出的新回合若完整成功并应用，则可以基于原输入和继承的相同目标建立新的 `told`，被替代分支上的证据随回退失效。`KnowledgeEvidence.evidenceId` 与获知事件 ID 一致，`source` 指向能供记忆引用的文本来源；030 必须沿 event ID 核验 mutation、applied receipt、回合终态、当前有效路径和传闻父链。缺任一依据则整个 evidence 不提供给候选。

presence revision 是 opaque CAS token，格式固定为 `sha256:` 加 64 位小写十六进制；由 session 身份、单调递增的有效历史 / 分支 revision、当前 scene、成员集合摘要及最后有效 presence mutation 身份派生。历史回退即使成员集合相同也不得复用旧 token。计划读取命令 `engine_get_scene_presence({ sessionId })` 返回 `{ sessionId, sceneId, presenceRevision, characters }`，仅返回已在场且完整目录中的 Character，最多 512 项、规范 JSON 总长最多 256 KiB；缺失基线、待恢复状态或超限时整体拒绝，不返回截断列表。区分界面读取与记忆证据扫描：后者每次最多读取最近有效路径的 4096 条记录 / 16 MiB，传闻链最多 8 跳；预算窗口外的来源 / 父链失败关闭，不因整局总长度拒绝窗口内证据。定向提交必须同时传 `recipientCharacterId` 与 `expectedPresenceRevision`；二者仅一个存在为 `app.bad-request` + `detail.reason=recipientRevisionPair`，token 过期为 `app.bad-request` + `detail.reason=stalePresenceRevision`，当前缺失 / 未知角色统一返回 `app.bad-request` + `detail.reason=targetUnavailable`，任何拒绝都先于玩家输入追加。成功接纳时将接收目标及其 `presenceRevision` 写入 `RoundAccepted`；恢复 / 重生成沿用这对值。旁白提交不携带 revision。读取遇到缺失基线或待恢复状态用现有 `engine.invalid-phase` 失败，超限为 `app.bad-request` + `detail.reason=presenceSnapshotLimit`；不返回截断列表。版本缺失时失败关闭。

## 验收标准

- [x] 在场状态由 Rust 可信规则 / 已提交记录建立；UI 只能读取和请求，不直接添加身份或修改成员关系；目录角色未配置初始在场规则时不得默认可交互。
- [x] 固定 / 动态身份共用稳定 ID；离场、回退、重启和旧选择行为有明确结果，不把注册身份等同于当前可交互；revision 对分支回退无 ABA 歧义。
- [x] `told`、`observed`、`rumor` 使用可审计且彼此不同的证据来源；观察范围 / 传闻传播链在结构上可核验，模型文本不授予权限。
- [x] 回合目标与新获知证据严格区分；已接纳目标可随恢复保留，但恢复本身不产生证据；失败 / 取消 / partial 路径不得伪造角色获知。
- [x] 当前 SceneCatalog / 世界操作如何承载在场和获知事件、完整事务回执、缺失字段的失败关闭行为明确。
- [x] 架构文件、IPC 契约、045 / 046 范围与依赖图一致；独立 subagent 评审通过。

## 风险与回退

场景成员若仅驻留 UI 或普通目录快照，会在重启 / 回退后失去可信因果依据。协议未能复用 023 的提交与恢复边界时，不接受定向目标；保留旁白输入并使未支持的动态选择明确不可用。

## 决策与工作记录

- 2026-10-12：为 030 已交付的固定角色定向后端入口预分配产品接入；动态在场需先设计，避免把已登记身份误作场景可见。记忆专属 IPC 归 031，025 / 023 不扩张。
