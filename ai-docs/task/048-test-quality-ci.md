## 目标与背景

让测试更能说明玩家可观察的行为与系统必须守住的边界，减少只为满足覆盖率数字而存在的断言；同时降低 Windows CI 的主要耗时，并保留三平台所需的运行验证。覆盖率用于发现未审查代码，不作为测试质量的替代指标。

GH Actions 的 PR #141 记录显示，Windows `coverage:rust` 为 238 秒（插桩编译约 51 秒，engine 测试约 53 秒，memory 测试约 123 秒）；macOS 同一步为 48 秒。memory 仓储测试普遍用真实磁盘 SQLite WAL 与同步提交。另有 main run #38333773526 的 Windows 原生 HMR 初始样式报告在 20 秒内超时；其 Rust coverage 步骤成功，应将这个原生测试启动问题与覆盖率耗时分开判断。

## 范围与非目标

- 审查 Rust 与 Web 测试的行为价值、测试夹具成本、脆弱实现断言和重复验证；优先保留授权 / 账本 / 恢复 / 持久性 / IPC / 原生平台等高风险行为。
- 以实际计时定位 Windows 热点，优化重复的完整持久化链路与不必要的磁盘夹具；durability 验证仍使用真实文件与同步语义。
- CI 只在一个基准平台生成覆盖率报告，其余平台仍运行普通 Rust 测试与相应原生验收；比较耗时并确保验证范围不缩水。
- 将前端和 Rust 覆盖门槛从“逐行填满”转为可维护的覆盖率基线，加上明确的高风险行为清单；覆盖率降低必须由行为验收和理由支撑，不以任意百分比替代测试设计。
- 修复或改善 HMR 原生测试的初始就绪判定与诊断，避免以重跑或单纯延长超时掩盖失败。
- 不以删除关键故障测试、全局关闭 SQLite 同步、跳过平台测试、隐藏未覆盖代码或单纯放宽数值门槛换取速度。
- 不在本任务中重构生产逻辑，除非修复暴露出的可复现行为缺陷。

## 实施步骤

1. 记录主要平台 CI 步骤耗时和测试分布，列出应保留的高风险行为合同。
2. 识别高成本与脆弱测试，区分持久性测试夹具和普通规则测试夹具；逐项说明保留或移除的理由。
3. 精简重复的持久提交准备，修正实现耦合的测试断言；用前后实测验证收益。
4. 调整覆盖率判定与 CI 平台分工，保留所有平台必要的普通测试和 native 验收。
5. 更新测试规范与 task 记录；由未参与实现的 subagent 独立评审，处理发现并复验。

## 风险与回退

减少运行覆盖的平台会降低跨平台覆盖率可见性；因此三平台仍执行普通 Rust 测试，且平台专属行为由原生集成验收。若普通测试在任一平台显著变慢或行为证明不足，恢复该平台覆盖步骤，并优先继续精简测试夹具。

## 决策与工作记录

- 2026-10-13：选择聚合 90% 作为最低覆盖线，避免为逐文件 100% 填测试；高风险行为清单另作验收，覆盖率数字不单独代表质量。
- 2026-10-13：GitHub Actions 实测指出 Windows 主要成本在 memory / engine 的磁盘测试执行，而非覆盖报告生成或单纯缓存未命中。
- 2026-10-13：保留三个平台的预编译 `cargo-llvm-cov` 安装；`bun install` 的 postinstall 会在工具缺失时源码安装它，若只在 Ubuntu 安装预编译版，Windows / macOS 可能新增源码编译成本。
- 2026-10-13：`gpt-6.1-sol` / `medium` 独立评审发现并修复四项问题：保持深色默认主题合同、让 HMR 错误报告允许缺少样式值并识别更新期异常、保留预编译覆盖工具安装、校正 CI 文档口径。修复后复核未发现遗留问题。
- 2026-10-13：PR #142 的三平台 CI 全部通过，Windows 原生验收成功，覆盖了本机 `BrokenPipe` 环境问题。该轮 Windows Rust workspace 测试为 273 秒，前一轮 Windows coverage 步骤为 238 秒；二者工作内容不同，但目前没有证据证明 Rust 测试墙钟时间已下降，因此不将 Windows 提速标记为完成。

测试质量、覆盖率分工、HMR 诊断和三平台原生验收均已调整；本地门禁、独立评审及 PR #142 三平台 CI 通过。Windows 原生测试通过，但 Rust 测试步骤耗时尚未证明优于基线；task 保持进行中，后续应基于分 crate / 测试执行计时继续定位热点，再决定是否接受当前耗时或追加优化。
